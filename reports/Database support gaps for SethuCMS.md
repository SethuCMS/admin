# SethuCMS Already Covers the Core Databases

SethuCMS's six adapters (memory, PostgreSQL, MySQL/MariaDB, SQLite, MongoDB, Firestore) already cover what every CMS competitor ships, and its real gaps are narrower than the planned list suggests. The first gap is verification. Every wire-compatible service the docs name (Supabase, Neon, Aurora, CockroachDB, TiDB, DocumentDB, Turso) has no test or fixture in the repos, so these are claims by design, not tested support. The second gap is SQL Server, which is the largest missing mainstream engine: **30.1% of developers use it** ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology)), it is in Directus and every data-connector product surveyed, and it needs more than a config entry because `sql-kit`'s `Dialect.name` is a closed union and has no hook for `OFFSET/FETCH` paging. Redis (28% usage) and DynamoDB (9.8%) are real differentiators but expensive: each is a full 1,200-1,750-line-class adapter with explicit scan semantics. Oracle is the one missing engine competitors carry (6 of 9 surveyed products) that SethuCMS has not planned. Recommended order: (1) verify and label Postgres-wire and MySQL-wire services in CI; (2) add libSQL/Turso as a thin client over the existing SQLite dialect; (3) widen `sql-kit` and ship SQL Server; (4) add a DocumentDB/Cosmos/FerretDB flavor of the Mongo adapter; (5) add read-only analytics adapters (ClickHouse, BigQuery, Snowflake, DuckDB); (6) then DynamoDB, then Redis/Valkey. Search engines, vector stores, graph and time-series databases should be sync targets or skipped, not content sources. Evidence quality is mixed: SethuCMS facts come from reading the local repos (strong), popularity from the Stack Overflow survey and npm (strong, but DB-Engines was only reachable via mirrors), and all effort estimates are judgment, not sourced.

## What SethuCMS supports today, and which of it is actually tested

The adapter contract is small: nine required methods (`connect`, `capabilities`, `introspect`, `find`, `get`, `create`, `update`, `delete`, `close`) and two optional ones (`createCollection`, `finishBulkLoad`) in [adapter.ts](file:///home/kasinadhsarma/sethucms-adapter-sdk/src/adapter.ts). Permissions, read-only enforcement, record validation, cursor signing, timeouts and error scrubbing belong to `GuardedAdapter`, not to each adapter ([guarded.ts](file:///home/kasinadhsarma/sethucms-adapter-sdk/src/guarded.ts)). The release gate is `defineConformanceSuite`, which runs through the guard and covers introspection, CRUD round trips, NOT_FOUND, exactly-once cursor pagination, filters and sorts, refusal of unsupported queries, read-only, hostile input and forged cursors ([conformance.ts](file:///home/kasinadhsarma/sethucms-adapter-sdk/src/testing/conformance.ts)). The model has hard assumptions: one single-column primary key per collection, string ids at the API, integer generated keys, and a closed set of 11 error codes. Databases without these (wide-column, composite-key, graph) need shims, as MongoDB does with a `_sethucms_counters` collection.

The cost of a new database is therefore not the interface. It is query translation for 11 operators plus and/or/not, sorting and paging; introspection into canonical types; honest capability flags; error mapping; and getting a real server into CI. The SQL adapters share `sql-kit` (1,065 lines) and own about 2,608 lines of client, settings, errors, introspection and type maps between them; MongoDB took 1,171 lines and Firestore 1,742 ([adapter notes](file:///home/kasinadhsarma/sethucms-admin/research_notes/Database%20support%20gaps%20for%20SethuCMS/sethucms_adapter_contract.md)). Capability presets already exist for `sql`, `mongodb`, `firestore` and `dynamodb` in `packages/core/src/capabilities.ts`, but no DynamoDB adapter exists.

What CI actually proves is a much shorter list than the docs imply. The `databases.yml` workflow runs live suites against PostgreSQL 16, MySQL 8, MariaDB 11, MongoDB 7, the Firestore emulator, plus a cross-database migration job; SQLite runs on real files via `node:sqlite` ([databases.yml](file:///home/kasinadhsarma/sethucms/.github/workflows/databases.yml)). The `docs/02-what-to-build.md` claim that "postgres covers Supabase, Neon, RDS, Aurora, Cloud SQL, AlloyDB, Azure PostgreSQL" and that mongodb covers "Atlas, DocumentDB, Cosmos Mongo API" is backed by no fixture; grep over code, tests and docs found none for CockroachDB, TiDB, Aurora, Neon, Supabase, DocumentDB, FerretDB, Turso, PlanetScale, YugabyteDB or AlloyDB. Only Atlas has a concrete mechanism (`srv: true`). Reading the code, the Postgres adapter sends startup options `-c statement_timeout` and `-c default_transaction_read_only=on` and calls `pg_get_serial_sequence` in `finishBulkLoad`; the MySQL adapter runs `SET SESSION sql_mode` and `SET SESSION TRANSACTION READ ONLY`. Services that reject startup options (transaction-mode poolers) or lack these functions are the likely breakage points, though that last step is my inference and no live run confirms it.

Third parties cannot add an adapter to a stock gateway without forking, except through the `grpc` kind. Built-in kinds are hard-coded in `apps/api/src/connections/adapters.ts`, and `main.ts` calls `createGateway({ config })` with no `adapters`, although `gateway.ts` merges extras if embedded. The Go and Python template repos carry an older proto (typed messages, `Batch`, `Subscribe`, no `Describe` or `FinishBulkLoad`) that differs from the SDK proto, so third parties should start from the SDK proto and `examples/python-minimal`, as `docs/23-grpc-adapters.md` itself half-admits. The admin app also hard-codes a per-database form list (`ADAPTER_FORMS`, 310 lines), so a new first-party adapter touches the registry, `package.json`, the admin form, the docs table and a CI job. That contradicts the `docs/05-adapter-contract.md` claim that "nothing in core, api or admin changes".

## What exists in the world, and what the market actually uses

Among developers, **PostgreSQL leads at 55.6%**, then MySQL 40.5%, SQLite 37.5%, SQL Server 30.1%, Redis 28%, MongoDB 24%, MariaDB 22.5%, Elasticsearch 16.7%, Oracle 10.6% and DynamoDB 9.8%; among professionals PostgreSQL is 58.2% ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology)). DB-Engines scores enterprise presence instead, putting Oracle first (about 1,100 points), then MySQL, SQL Server and PostgreSQL, with MongoDB fifth, Snowflake sixth and Redis eighth ([HelloGitHub mirror](https://hellogithub.com/report/db-engines)). The two rankings diverge sharply on Oracle (first by score, last of the big relational engines by developer usage), and a CMS gateway's audience looks more like the survey's, so the survey should drive priority and DB-Engines should justify only enterprise-facing work such as SQL Server and Oracle. Weekly npm downloads confirm the Node ecosystem order: pg 93.7M, mysql2 23.2M, better-sqlite3 15.8M, mssql 4.7M (tedious 7.3M), oracledb 1.2M ([npm API](https://api.npmjs.org/downloads/point/last-week/pg)), with the caveat that ORMs and CI inflate the top numbers.

The taxonomy the question asks for resolves into a handful of integration classes, and the class matters more than the product name. Relational and NewSQL engines are mostly wire-compatible with Postgres or MySQL. CockroachDB speaks the Postgres wire protocol and reports PostgreSQL 18, but its integer division returns decimals, INT is always 64-bit, session-scoped advisory locks are unsupported, and deadlocked transactions fail with a client-retryable error ([CockroachDB docs](https://docs.cockroachlabs.com/docs/stable/postgresql-compatibility)). TiDB targets MySQL 5.7 and 8.0 but has no stored procedures, triggers or `SKIP LOCKED`, and its auto-increment ids are unique but not sequential across servers, with `AUTO_RANDOM` recommended ([TiDB docs](https://docs.pingcap.com/tidb/stable/mysql-compatibility/)). Aurora DSQL omits extensions, `TRUNCATE`, `SAVEPOINT` and (per localized pages) foreign keys, sequences and triggers ([AWS docs](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility-unsupported-features.html)). Spanner's PostgreSQL interface needs the PGAdapter sidecar ([Spanner docs](https://docs.cloud.google.com/spanner/docs/postgresql-interface)). YugabyteDB, AlloyDB, SingleStore, Vitess and OceanBase are described in the notes only from background knowledge and are unverified.

Serverless and BaaS products are mostly Postgres underneath. Supabase's shared pooler on port 6543 runs in transaction mode and does not support prepared statements, while session mode on 5432 does ([Supabase KB](https://supabase.com/kb/troubleshooting/disabling-prepared-statements-qL8lEL)); Neon uses PgBouncer in transaction mode with a `-pooler` host and offers HTTP and WebSocket serverless drivers ([Neon docs](https://neon.com/docs/connect/choose-connection.md)); Prisma Postgres has accepted direct TCP since October 2025 ([Prisma blog](https://blog.prisma.io/blog/cloudflare-unikernels-and-bare-metal-life-of-a-prisma-postgres-query)); PlanetScale launched a Postgres product in 2025 that is explicitly not Vitess ([PlanetScale](https://planetscale.com/blog/planetscale-for-postgres-is-generally-available)); Vercel Postgres has been folded into Neon ([Vercel docs](https://vercel.com/docs/postgres)); the old Xata Lite was retired on 2026-02-28 and the new Xata is vanilla Postgres ([Xata](https://xata.io/blog/serverless-postgres-platform)). The genuinely different ones are Turso/libSQL (Hrana over HTTP or WebSocket, [Turso docs](https://docs.turso.tech/sdk/http/quickstart.md)), Cloudflare D1 (SQLite behind a REST `/query` endpoint, [Cloudflare](https://codex-container-api-docs.previews.developers.cloudflare.com/d1/best-practices/query-d1/index.md)), Convex (developer-defined functions, no generic table API, [Convex docs](https://docs.convex.dev/api/classes/browser.ConvexHttpClient)), Appwrite (its own TablesDB REST API, [Appwrite](https://appwrite.io/docs/products/databases/tablesdb/tables.md)) and PocketBase (SQLite behind a rules-governed REST API, [PocketBase](https://pocketbase.io/docs/api-rules-and-filters/)). Prisma and Drizzle are not databases; they are schema DSLs and clients over the customer's database. Supporting them means introspecting the live database (the universal path) and optionally importing `schema.prisma` for naming, enum and relation hints, not writing a runtime adapter.

For NoSQL, the MongoDB wire family (MongoDB, Amazon DocumentDB, Azure Cosmos DB for MongoDB, FerretDB 2.x) shares the official `mongodb` driver, each with feature gaps ([AWS](https://docs.aws.amazon.com/documentdb/latest/developerguide/compatibility.html), [Microsoft](https://learn.microsoft.com/en-us/azure/cosmos-db/mongodb/introduction), [Linuxiac](https://linuxiac.com/ferretdb-2-0-open-source-document-database-goes-ga/)). Everything else needs its own driver. DynamoDB's Query requires a partition key, and Scan reads up to 1 MB before applying filters, so filtered pages can come back empty with more matches remaining ([AWS Query](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Query.html), [Scan](https://docs.aws.amazon.com/de_de/amazondynamodb/latest/developerguide/Scan.md)). Cassandra rejects full-partition scans without `ALLOW FILTERING` and orders only by clustering columns ([Cassandra docs](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html)). Cosmos NoSQL pages can be short or empty and continuation tokens are unavailable for GROUP BY/DISTINCT ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/query/pagination)). Redis moved to SSPL in 2024 and added AGPLv3 with Redis 8, which prompted the Valkey fork ([Redis blog](https://redis.io/blog/agplv3/)). HBase, FoundationDB, RethinkDB and PouchDB show stale or absent Node clients (hbase 0.6.1 last published 2022, foundationdb 2.0.1 in 2023) and are not worth building. The specialised classes (search, vector, graph, time-series, warehouse) are covered in the integration section below.

## How SethuCMS compares with competitors and where it falls short

Content-first CMSs are narrow: Strapi supports MySQL, MariaDB, PostgreSQL and SQLite and rejects MongoDB ([Strapi docs](https://docs.strapi.io/cms/configurations/database)); Payload supports MongoDB, Postgres and SQLite ([Payload docs](https://payloadcms.com/docs/database/overview)); Keystone supports PostgreSQL, MySQL and SQLite ([Keystone docs](https://keystonejs.com/docs/config/config)). Directus is the broad one, with `DB_CLIENT` values for pg, mysql, oracledb, mssql, sqlite3 and cockroachdb ([Directus docs](https://directus.com/docs/configuration/database)). Data-connector products go wider still: Hasura v2 ([docs](https://hasura.io/docs/2.0/databases/overview/)), Appsmith ([docs](https://docs.appsmith.com/connect-data/reference)) and Metabase ([docs](https://www.metabase.com/docs/latest/databases/connecting)) add SQL Server, Oracle, and warehouses, and Appsmith, Retool and Budibase add DynamoDB. SethuCMS already beats every CMS peer except Directus on breadth, and is the only one besides Payload with NoSQL. Its identity as "CMS over any database" means it is judged against the connector products, however, and there the missing rows are MSSQL (in 6 of 9 surveyed products), Oracle (6 of 9), DynamoDB (3), Redis (1-2) and CockroachDB (2).

Ranking the misses by adoption and fit gives a clear order. The first tier is verification of Postgres-wire and MySQL-wire services, because they carry the largest user base (Postgres at 55.6% and Supabase and Neon riding on it) for the smallest cost, with MariaDB (22.5%) already CI-tested. Next is SQL Server (30.1% usage, DB-Engines #3, Directus parity). Third are libSQL/Turso and the MongoDB-wire flavors, which ride on existing dialect or driver code. Fourth are read-only analytics adapters, where the clients are heavily used (`@clickhouse/client` 4.8M weekly, `@google-cloud/bigquery` 6.9M, `snowflake-sdk` 3.6M, `@duckdb/node-api` 3.2M, [npm API](https://api.npmjs.org/downloads/point/last-week/%40clickhouse%2Fclient)) though Stack Overflow usage is only 2-6.5% each. Fifth are Redis/Valkey (28% usage, but key-pattern modeling makes it a poor fit for a collection model) and DynamoDB (9.8%, but dominant inside AWS; `@aws-sdk/client-dynamodb` has 17.7M weekly downloads). Oracle is a deliberate "enterprise on demand" item: 10.6% usage and 1.2M weekly driver downloads, but the biggest dialect effort. Elasticsearch (16.7% usage) has the highest remaining usage of any unplanned engine, but in CMS ecosystems it is always a derived index synced from a primary store, as with Meilisearch plugins for Strapi, Directus and Payload ([Meilisearch](https://www.meilisearch.com/integrations/strapi), [Directus](https://directus.io/extensions/directus-extension-meilisearch-integration)).

## How to integrate each missing database

The integration cost falls into four tiers, defined by how much of `sql-kit` and the existing adapters can be reused. These tiers and all effort figures are my estimates drawn from the code reading and driver facts, not project statements.

| Class | Examples | Driver | Adapter work | Main risks |
|---|---|---|---|---|
| Tier 0, config and CI only | Supabase, Neon, Aurora PG, AlloyDB, Prisma Postgres (TCP), Nile, PlanetScale Postgres, Xata, CockroachDB, YugabyteDB, TimescaleDB, pgvector; TiDB, Aurora MySQL, PlanetScale MySQL; Atlas | `pg`, `mysql2`, `mongodb` | One live-test run per service with the env-var-gated conformance suite; compatibility patches as found | Transaction-mode poolers rejecting startup `options` and prepared statements; CockroachDB `40001` retries; TiDB non-sequential ids; DSQL lacking sequences/FKs/`SAVEPOINT`; Supabase service-role bypassing RLS |
| Tier 1, small | libSQL/Turso (reuse `sqliteDialect`); DuckDB; MongoDB-wire flavors (DocumentDB, Cosmos RU/vCore, FerretDB) | `@libsql/client`; `@duckdb/node-api` (2.0.0-r.1); `mongodb` | New client, settings, errors, introspect; a `flavor` field with feature probes for Mongo | libSQL needs a remote client (the SQLite adapter only opens local files in `SETHUCMS_SQLITE_DIR`); DuckDB is pre-release-numbered and file-locking; DocumentDB/Cosmos lack some MQL (collation, `$text`, transactions) |
| Tier 2, medium (touch `sql-kit`) | SQL Server; Oracle; ClickHouse, BigQuery, Snowflake, Databricks, Redshift (read-only) | `mssql` (tedious 20.3.8, Node 22+); `oracledb` (Thin mode needs DB 12.1+); `@clickhouse/client`, `@google-cloud/bigquery`, `snowflake-sdk`, `@databricks/sql` | Widen `Dialect.name`, add `columnType`/`keyColumn` cases and a limit/offset hook; SQL Server needs `OFFSET/FETCH` (requires `ORDER BY`), `OUTPUT INSERTED`, bracket quoting, `@name` params and `sys`/`INFORMATION_SCHEMA` introspection; Oracle needs uppercase folding, `ALL_*` views, `:n` binds, empty-string-as-NULL | Oracle is the largest dialect gap; warehouses have no cheap point lookups or primary keys, so row identity is unclear |
| Tier 3, large (full adapter, about 1,200-1,750 lines) | DynamoDB; Redis/Valkey; Cassandra/Scylla; Cosmos NoSQL native; Couchbase; Elasticsearch/OpenSearch as source; graph | `@aws-sdk/lib-dynamodb`; `ioredis`/`@valkey/valkey-glide`; `cassandra-driver`; `@azure/cosmos` | Schema inference, id strategy, honest capability flags, scan budgets | Scan cost on customer accounts, empty filtered pages, key-pattern modeling for Redis, `ALLOW FILTERING`, RU throttling (429) |

The SQL Server path deserves detail because it is the first thing to build. The `Dialect` interface already covers quoting, placeholders, LIKE operator, `RETURNING`, inline limits and datetime parameters, but `name` is typed `'postgres' | 'mysql' | 'sqlite'` and `buildSelect` hard-codes `LIMIT n OFFSET m`. A new dialect object is about 50 lines; the genuine work is the paging hook, the `OUTPUT` clause, the DDL cases, the `IDENTITY` primary key and introspection through `INFORMATION_SCHEMA`. The `mssql` driver encrypts by default, supports Azure AD modes and names parameters `@name`, but should not use `@p{n}` as names ([node-mssql docs](https://tediousjs.github.io/node-mssql/)). Widening the union also fixes the problem that no outside party can add an SQL dialect without patching `sql-kit`.

For DynamoDB and Redis, the capability model decides everything. The honest DynamoDB profile is key-condition queries plus explicit, budgeted scans with `LastEvaluatedKey` mapped into the signed opaque cursor, no offset, sort only on the sort key, and a loop that tolerates empty filtered pages. Redis needs user-defined key patterns as "collections", SCAN with no ordering or filtering, and a hard block on `KEYS` and destructive commands. Dragonfly, KeyDB and Upstash (Redis protocol, plus REST for Upstash) need no separate adapter. The existing `dynamodb` capability preset is a starting point, though the notes could not confirm its exact flags beyond its existence.

Specialised stores should mostly not become sources. Search engines are a sync-target problem: an index-on-publish hook for Meilisearch or Typesense (open-source REST clients, 1.0M and 1.3M weekly downloads) is more valuable than reading Elasticsearch as a collection, and Elasticsearch and OpenSearch are two diverging forks with licensing churn (AGPL added to Elasticsearch in 2024, OpenSearch at the Linux Foundation, [InfoQ](https://www.infoq.com/news/2024/09/elastic-open-source-agpl)). pgvector and TimescaleDB are Postgres extensions and need only type-mapping in the Postgres adapter (`vector` shown read-only). Pinecone, Qdrant, Weaviate, Milvus, Chroma, Neo4j, Memgraph, ArangoDB, InfluxDB and QuestDB have no evidence of use as CMS content stores in the notes and should be skipped unless customers ask. Gateway state is a separate matter: Postgres state is refused for `SETHUCMS_WORKSPACES=open` because its tables, single state row (`id = 1`), audit table and NOTIFY channels are un-namespaced, so two workspaces would share one row. A per-workspace schema plus a shared pool is a medium change touching about 900 lines of the store family ([workspaces.ts](file:///home/kasinadhsarma/sethucms/apps/api/src/boot/workspaces.ts), [postgres.ts](file:///home/kasinadhsarma/sethucms/apps/api/src/store/postgres.ts)). It does not affect whether a customer's content database is Postgres.

## Which claims are verified, unverified, or contradicted

Verified by direct reading: the adapter interface, `GuardedAdapter` duties, the conformance scenarios, `sql-kit`'s closed `Dialect.name` union, the hard-coded registry, the gRPC proto and stale templates, the Postgres workspace refusal and its table design, and what CI runs. Verified by fetched external sources: Stack Overflow 2025 usage figures, npm versions and weekly downloads read live on 2026-11-05, and the competitor database lists, CockroachDB and TiDB compatibility pages, DynamoDB/Cassandra/Cosmos query behavior, Redis licensing, and the Supabase, Neon and Prisma pooler facts. Unverified (background knowledge or secondary mirrors only): all effort estimates; the SQL Server and Oracle dialect details; YugabyteDB, AlloyDB, SingleStore, Vitess and OceanBase compatibility; the Postgres-wire breakage hypotheses; whether any wire-compatible service passes the live suites; Couchbase index requirements; the warehouse auth and latency specifics; the DB-Engines figures, because db-engines.com failed with a certificate error and every score comes from mirrors; and the Directus minimum versions, which come from README mirrors.

The sources contradict one another in several places. The SethuCMS docs disagree with CI: `docs/18-adapters.md` and the package READMEs say MySQL was tested only against Dolt, MongoDB only against FerretDB 1.24 and Firestore only against an in-memory fake, and `docs/18` also says MySQL/MariaDB/MongoDB/Firestore "have not been run through these tests", yet `databases.yml` and the adapters root README show live runs on MySQL 8, MariaDB 11, MongoDB 7 and the Firestore emulator; the CI file and root README should be treated as authoritative. `docs/05-adapter-contract.md` lists `batch` and `subscribe` operations that are not in the real `Adapter` interface and says keyset pagination while the code uses offset (the Postgres README says keyset is "planned"), and its claim that a new adapter touches nothing outside the adapter package is wrong. `docs/11-roadmap.md` and the adapters README say only SQL Server and DynamoDB are not started, whereas the task framing also lists Redis as planned, which only `docs/02-what-to-build.md` appears to say. Among the external sources, DB-Engines mirrors differ (Oracle 1,096 in the November snapshot versus 1,132 in July; PostgreSQL 689 versus 687; Redis about 153 versus 163); Redis's Stack Overflow figure is quoted as roughly 28% in one note and as 28% versus 30.7% in another, and MongoDB's clean percentage (24%) appears in one note while the other could not find one; Prisma Postgres TCP availability changed from "unavailable" in early-2025 material to GA in October 2025, so older pages are superseded; the Vercel Postgres-to-Neon migration is dated December 2024 by one source and June 2025 by another; the Oracle npm version (26.0.0) and the v7.0.0 release notes do not line up; ORM download counts disagree by a wide margin between Drizzle and Prisma; and the vector and Snowflake rankings in the DB-Engines mirrors conflict with each other.

## Conclusion

The central finding is that SethuCMS's biggest database gap is evidence, not engines: it can move from a short tested list to a long, honestly labelled list in days by running its own conformance suite against services it already names, and that single step serves more users than any new adapter. The second finding is that the adapter contract is cheap but the SQL layer is not yet open. Widening one type union and adding one paging hook buys SQL Server, Oracle and the warehouses, and also fixes the third-party dialect problem, so that work should come before the large DynamoDB and Redis adapters, whose poor fit for a filter-sort-page collection model makes them the highest-cost, lowest-leverage items despite being on the plan.

The decision that remains open is demand. The notes contain no SethuCMS customer data, so the ordering below SQL Server rests on public adoption and competitor parity. The roadmap should be re-ranked against real connection requests once the Tier 0 verification work produces a public compatibility table, and the ecosystem question (a plugin loader and refreshed gRPC templates) will decide whether the long tail is built by SethuCMS or by others.
