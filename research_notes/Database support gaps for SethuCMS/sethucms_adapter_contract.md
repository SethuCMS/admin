## 1. What is the adapter interface, and what must the conformance suite pass?

### Takeaway
An adapter is a thin translator implementing 9 required methods (`connect`, `capabilities`, `introspect`, `find`, `get`, `create`, `update`, `delete`, `close`) plus 2 optional (`createCollection`, `finishBulkLoad`). Permissions, read-only, record validation, cursor signing, timeouts and error hiding are NOT the adapter's job; `GuardedAdapter` does them for every adapter. Release gate is `defineConformanceSuite` (8 scenarios).

### Cited Findings
- Interface: `type`, `connect(ConnectInput)`, `capabilities()`, `introspect(): CollectionDefinition[]`, `find(collection, query, position): {records, nextPosition?}`, `get(collection,id)` returning record or null, `create`, `update` (throw NOT_FOUND if missing), `delete`, `close()` (safe to call twice); optional `createCollection?` and `finishBulkLoad?` — `/home/kasinadhsarma/sethucms-adapter-sdk/src/adapter.ts` (lines 44-109).
- `ConnectInput` = `{connectionId, config (non-secret), credentials (secret, vault-resolved), readOnly}` — `/home/kasinadhsarma/sethucms-adapter-sdk/src/adapter.ts` (19-27).
- Records are plain JSON with canonical types (ISO strings for dates, base64 for binary) — `/home/kasinadhsarma/sethucms-adapter-sdk/src/adapter.ts` (12-16).
- Pagination: cursor mandatory (`pagination.cursor: true` is a literal type), offset optional. Adapter returns at most `query.page.limit` records and an opaque, JSON-serialisable `nextPosition` only when more exist; the guard signs it into the client cursor and trims over-returns — `/home/kasinadhsarma/sethucms-adapter-sdk/src/guarded.ts` (195-214) and `/home/kasinadhsarma/sethucms/packages/core/src/capabilities.ts` (38-41). SQL adapters use `{offset}` as position and fetch limit+1 rows to detect a next page — `/home/kasinadhsarma/sethucms-adapters/packages/postgres/src/postgres-adapter.ts` (100-119).
- Query model: `Query = {collection, filter?, sort?, projection?, page{limit,cursor}}`; filter is a tree of comparison / `and` / `or` / `not`; operators `eq ne lt lte gt gte in nin contains startsWith exists`; limits default 50, max 500, depth 8, 100 nodes, 4 sort fields, 200 `in` values — `/home/kasinadhsarma/sethucms/packages/core/src/query-ast.ts` and `/home/kasinadhsarma/sethucms/packages/core/src/field-types.ts` (31-43).
- Capability flags: `joins`, `transactions` (none/single-document/multi-document), `filters{or, inequality full/single-field/none, fullText}`, `sort` (any-field/indexed-only/key-only), `pagination{cursor:true, offset}`, `aggregations`, `realtime`, `schema` (enforced/inferred), `writes`. Defaults are restrictive (everything off, sort key-only, schema inferred, writes false). Presets exist for `sql`, `mongodb`, `firestore`, `dynamodb` — `/home/kasinadhsarma/sethucms/packages/core/src/capabilities.ts` (29-166). The `dynamodb` preset exists but no DynamoDB adapter does.
- The guard validates the query and checks it against `capabilities()` via `planQuery` (unsupported -> `CAPABILITY_UNSUPPORTED`, never approximated) — `/home/kasinadhsarma/sethucms-adapter-sdk/src/guarded.ts` (195-200); README "What the guard does for you" in `/home/kasinadhsarma/sethucms-adapter-sdk/README.md`.
- Read-only: connections are read-only unless explicitly `false` (fail closed); writes also need `adapter.capabilities().writes`; `applyReadOnly` turns `writes` off — `/home/kasinadhsarma/sethucms-adapter-sdk/src/guarded.ts` (176-183, 278-285). Adapters are encouraged (not required) to also open read-only sessions: Postgres sets `default_transaction_read_only=on`, MySQL runs `SET SESSION TRANSACTION READ ONLY` — `/home/kasinadhsarma/sethucms-adapters/packages/postgres/src/client.ts` (165-170), `/home/kasinadhsarma/sethucms-adapters/packages/mysql/src/client.ts` (~54-60).
- Record validation (no unknown, generated or read-only fields), id validation (non-empty, <=256 chars, no control chars), 15 s default timeout, and any non-`SethuError` thrown by an adapter is replaced by generic `INTERNAL` with the original kept only as cause — `/home/kasinadhsarma/sethucms-adapter-sdk/src/guarded.ts` (162-163, 234-267, 288-326).
- Error codes (fixed 11): CONNECTION_FAILED, AUTH_FAILED, FORBIDDEN, READ_ONLY, NOT_FOUND, CONFLICT, VALIDATION_FAILED, CAPABILITY_UNSUPPORTED, RATE_LIMITED, TIMEOUT, INTERNAL — `/home/kasinadhsarma/sethucms/packages/core/src/errors.ts` (8-20). Each adapter has its own `errors.ts` mapping driver codes (e.g. Postgres SQLSTATE 28P01->AUTH_FAILED, 23505->CONFLICT, 25006->READ_ONLY) and never copies driver text — `/home/kasinadhsarma/sethucms-adapters/packages/postgres/src/errors.ts`; rule restated in `/home/kasinadhsarma/sethucms-adapters/AGENTS.md`.
- Schema introspection returns `CollectionDefinition[]` with canonical types (`string text integer decimal boolean datetime date json array binary geopoint reference`). Postgres: tables without a primary key, with a composite key, or with non-plain-identifier names are skipped; unmappable types become lossy `string`; FKs become many_to_one relations — `/home/kasinadhsarma/sethucms-adapters/packages/postgres/README.md` ("Introspection"), `/home/kasinadhsarma/sethucms-adapters/packages/postgres/src/type-map.ts`. Single-column primary key is a hard assumption (`primaryKeyOf`).
- Conformance suite (`defineConformanceSuite(test, {label, prepare({readOnly})})`): `prepare` must return a connected adapter with EMPTY storage for the fixed `items` collection (id integer generated PK, title string required maxLength 200, score integer, status string). Scenarios: (1) introspect gives canonical types, (2) create/get/update/delete round trip, (3) missing record -> NOT_FOUND, (4) cursor pagination returns every record exactly once, (5) filters and sorting, (6) unsupported queries refused with CAPABILITY_UNSUPPORTED (branches on declared caps: no-or, no-inequality, key-only sort), (7) read-only rejects every write with READ_ONLY, (8) hostile input (SQL injection text, operator injection, wildcards, mass assignment) treated as data or rejected, (9) forged/reused cursors rejected — `/home/kasinadhsarma/sethucms-adapter-sdk/src/testing/conformance.ts` (37-51, 188-474), README "Writing an adapter" in `/home/kasinadhsarma/sethucms-adapter-sdk/README.md`.
- Suite is driven through the GuardedAdapter, so guard and adapter are verified together — `/home/kasinadhsarma/sethucms-adapter-sdk/src/testing/conformance.ts` (74-99).
- D/02 "Definition of done": also a separate security suite (injection, identifier allowlist), accurate capability flags, README documenting services/auth modes/limits — `/home/kasinadhsarma/sethucms-docs/docs/02-what-to-build.md` (54-58). D/05 also lists `batch` and `subscribe` operations, but they are NOT in the real `Adapter` interface (aspirational, stale doc) — `/home/kasinadhsarma/sethucms-docs/docs/05-adapter-contract.md` vs `/home/kasinadhsarma/sethucms-adapter-sdk/src/adapter.ts`.
- Dev loop per adapter (typical): package with `src/{adapter,client,settings,errors,introspect,type-map}.ts`, unit tests with an injected fake `clientFactory`, plus a live test gated by an env var such as `SETHUCMS_TEST_PG_URL` that runs the conformance suite on a scratch schema — `/home/kasinadhsarma/sethucms-adapters/packages/postgres/tests/live.test.ts`, `/home/kasinadhsarma/sethucms-adapters/README.md`.

### Inferences
- The contract is small. The real cost of a new database is not the interface but (a) query translation for the 11 operators + and/or/not + sort + keyset/offset paging, (b) introspection into canonical types, (c) honest capability flags, (d) error mapping, (e) getting a real server into CI so the live conformance test runs.
- Hard limits baked into the model: one single-column primary key per collection, ids as strings in `get/update/delete`, integer generated keys. Databases without these (wide-column, composite-key-only, graph) need adapter-side shims (as MongoDB/Firestore do with a counter collection).

### Gaps
- `assertValidRecord` / `planQuery` internals were not read in detail (only their call sites).
- Whether the "security suite" named in D/02 exists as a separate shared kit: not found; only the hostile-input scenario inside conformance.

## 2. How much of a new SQL dialect does sql-kit already provide, and what does a non-SQL store need?

### Takeaway
sql-kit provides all filter/sort/paging/insert/update/delete/DDL builders and row normalisation; a dialect is a ~50-line `Dialect` object plus per-database pieces (client, settings, errors, introspection, type map). But the `Dialect` type is a CLOSED union (`'postgres'|'mysql'|'sqlite'`) and DDL/pagination syntax is hard-coded in places, so dialects that differ in LIMIT/OFFSET or quoting (SQL Server, Oracle) require sql-kit edits, not just a new object. Wire-compatible databases need almost nothing; a non-SQL store is a full adapter (~1,200-1,750 lines for Mongo/Firestore).

### Cited Findings
- `Dialect` members: `name`, `quote`, `placeholder(n)`, `likeOperator` (ILIKE/LIKE), `likeEscape`, `notEqual` (null-safe), `arrayContains`, `nullsOrdering`, `returning`, `inlineLimits`, `arrayAsJson`, `insertDefaults`, `datetimeParam`, `booleanParam`. Three dialect objects exist (postgres, mysql, sqlite), each ~25 lines — `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/dialect.ts` (13-154).
- `name` is typed `'postgres' | 'mysql' | 'sqlite'` — `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/dialect.ts` (14). `ddl.ts` switches exhaustively on `dialect.name` for column types and primary-key syntax and special-cases `'mysql'` for varchar cap and `ENGINE=InnoDB` — `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/ddl.ts` (50-58, 234, 263, 282-298). So a new dialect must add a case in `columnType` (canonical type -> native type for all 12 canonical types) and `keyColumn` (generated-PK syntax).
- `buildSelect` emits fixed `ORDER BY ... LIMIT n OFFSET m` (optionally `NULLS FIRST/LAST`) and `RETURNING` only when `dialect.returning`; identifier quoting is validated against `/^[A-Za-z_][A-Za-z0-9_]{0,62}$/` — `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/builders.ts` (299-353, 404-420), `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/dialect.ts` (70-78). There is no dialect hook for `OFFSET .. FETCH NEXT` / `TOP`, so SQL Server/Oracle need a new `limitClause` hook or a builder change.
- Everything else is shared: filters, `LIKE` escaping, `in`/`nin`, array contains, parameter numbering, insert/update/delete, `buildCreateTable`, `normalizeRow` (JSON/bigint/boolean/date normalising), `dropBrokenRelations` — `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/index.ts`. The driver seam is the 2-method `SqlClient {query(text, values), close()}` returning `{rows, insertId?, affected?}` — `/home/kasinadhsarma/sethucms-adapters/packages/sql-kit/src/client.ts`.
- What each SQL adapter still owns (the per-database "copy-and-fill" work): `client.ts` (driver pool, TLS default on, session read-only, statement timeout), `settings.ts` (validate host/port/db/ssl/pool/timeout; user/password come from credentials), `errors.ts` (native code -> platform code), `introspect.ts` (catalog queries), `type-map.ts`, the adapter class (~300 lines, near-identical across pg/mysql/sqlite), plus `createCollection` and `finishBulkLoad`. Line counts: postgres+mysql+sqlite src total 2,608 lines vs sql-kit 1,065 — `wc -l` over `/home/kasinadhsarma/sethucms-adapters/packages/{postgres,mysql,sqlite,sql-kit}/src/*.ts`. Introspection is the only per-dialect SQL that is truly new (mysql `introspect.ts` 184 lines, postgres 212, sqlite 155).
- Engine quirks the existing adapters already absorb: MySQL has no RETURNING (adapter re-reads after write, uses `insertId`), inline LIMIT/OFFSET, JSON stored as text, MariaDB JSON detected via `json_valid` check constraint, strict sql_mode set per connection, `+FOUND_ROWS` — `/home/kasinadhsarma/sethucms-adapters/packages/mysql/src/mysql-adapter.ts`, `/home/kasinadhsarma/sethucms-adapters/packages/mysql/src/client.ts`, `/home/kasinadhsarma/sethucms-adapters/packages/mysql/src/introspect.ts` (54-90). Postgres `finishBulkLoad` uses `pg_get_serial_sequence`/`setval` — `/home/kasinadhsarma/sethucms-adapters/packages/postgres/src/postgres-adapter.ts` (207-233).
- Non-SQL: MongoDB adapter 1,171 lines (`translate.ts` filter->BSON, `infer.ts` schema sampling, counter collection `_sethucms_counters` for integer ids, `_sethucms_schemas` for declared shapes, rejects `$`-operators in values) — `/home/kasinadhsarma/sethucms-adapters/packages/mongodb/src/mongo-adapter.ts`, `/home/kasinadhsarma/sethucms-docs/docs/18-adapters.md` (55-71). Firestore adapter 1,742 lines (`translate.ts` 410, `scan.ts` for bounded text scans, `files.ts` for file storage, `infer.ts`), refuses OR+inequality combos, uses `PRESETS.firestore` — `/home/kasinadhsarma/sethucms-adapters/packages/firestore/src/`, `/home/kasinadhsarma/sethucms-docs/docs/18-adapters.md` (73-91). Both use preset capability sets from CORE and must emulate the generated integer key, schema discovery (schema `inferred`), and error mapping.
- Key-value (DynamoDB, Redis) are planned in D/02 as "key conditions only; scans are explicit and costly" and D/11 says "Not started: SQL Server, DynamoDB" — `/home/kasinadhsarma/sethucms-docs/docs/02-what-to-build.md` (30), `/home/kasinadhsarma/sethucms-docs/docs/11-roadmap.md` (12). README says "SQL Server and DynamoDB are not started" — `/home/kasinadhsarma/sethucms-adapters/README.md`. D/28 "SQL Server: Not supported yet" — `/home/kasinadhsarma/sethucms-docs/docs/28-run-it-yourself.md` (55, 76).

### Inferences
- Effort tiers (author's estimate, not a project statement):
  - Tier 0, config only (0 code): databases that speak the Postgres or MySQL wire protocol AND `information_schema` closely enough (see section 4). Cost is a CI job and compatibility fixes.
  - Tier 1, small (new dialect object + client + settings + errors + introspect + type-map, reusing builders): SQL databases with LIMIT/OFFSET, `?`/`$n` params, quoted identifiers (e.g. a CockroachDB-native or TiDB-native adapter only if wire compatibility fails; libSQL/Turso remote client reusing `sqliteDialect`; DuckDB). Sizes comparable to sqlite (≈ 900 lines incl. tests excluded) minus builders.
  - Tier 2, medium (also touch sql-kit: widen `Dialect.name` union, add `columnType`/`keyColumn` cases, add a limit/offset hook): SQL Server, Oracle, Snowflake/BigQuery-style (these also lack plain RETURNING or need OUTPUT clause).
  - Tier 3, large (full adapter like Mongo/Firestore, ~1,200-1,750 lines + schema inference + id strategy): DynamoDB, Redis, Cosmos native, Cassandra/Scylla, Elasticsearch/OpenSearch, graph DBs.
- Because `Dialect.name` is a closed union and `ddl.ts` switches on it, a third party cannot add an SQL dialect outside the repo without forking/patching sql-kit (they can write their own builders instead, or use gRPC).

### Gaps
- `builders.ts` was read via grep, not line-by-line; exact behaviour of sort + keyset (D/05 says keyset pagination for SQL, but code uses offset; README of postgres says keyset is "planned") — offset is what is implemented.
- Did not size the effort of an SQL Server adapter beyond the structural reasoning above.

## 3. Can a third party add an adapter without forking? How are connections configured and secrets stored?

### Takeaway
Yes, but only via the `grpc` kind (out-of-process, any language) for a stock gateway. The in-process "package plugin" path exists only for people who embed the gateway: `createGateway({ adapters })` merges extra kinds, but the shipped `main.ts` passes none and there is no env/config plugin loader. Built-in kinds are hard-coded imports in one file and linked via `link:` paths in `package.json`.

### Cited Findings
- Registry: `builtInAdapters()` returns a hard-coded record: `memory, postgres, mysql, sqlite, mongodb, grpc, firestore`; each entry is `{label, create(config)->Adapter, networkHost(config)->string|null, seed?, wantsSeed?, declareCollections?, files?}`. File header: "Adding a database type means adding one entry here" — `/home/kasinadhsarma/sethucms/apps/api/src/connections/adapters.ts` (1-6, 27-57, 110-173).
- Adapters are imported statically and linked from sibling folders: `"@sethucms/adapter-postgres": "link:../../../sethucms-adapters/packages/postgres"` etc. — `/home/kasinadhsarma/sethucms/apps/api/package.json` (16-22). SDK/core are also not yet published, linked from sibling folders — `/home/kasinadhsarma/sethucms-adapters/README.md` ("Working on it locally").
- Extension seam: `kinds: { ...builtInAdapters(...), ...options.adapters }` in `/home/kasinadhsarma/sethucms/apps/api/src/gateway.ts` (242-247). `main.ts` calls `createGateway({ config })` with no `adapters` — `/home/kasinadhsarma/sethucms/apps/api/src/main.ts` (21). grep found no plugin loader or `SETHUCMS_ADAPTER*` env var in `apps/api/src`.

Stored shape `StoredConnection {id,name,adapterType,mode,config,credentials,exposed,known,...}` — `/home/kasinadhsarma/sethucms/apps/api/src/store/state.ts` (22-40).

- Admin UI has hard-coded per-database connection forms (`ADAPTER_FORMS` keyed by adapter id, 310 lines) with fields tagged `where: 'config' | 'credentials'`; an adapter not listed there needs a form entry — `/home/kasinadhsarma/sethucms-admin/src/lib/adapterForms.ts`. The gateway exposes `registry.adapterTypes()` at the admin route — `/home/kasinadhsarma/sethucms/apps/api/src/routes/admin.ts` (42).
- Docs claim the gateway adapter "Nothing in core, api or admin changes" for a new adapter (`/home/kasinadhsarma/sethucms-docs/docs/05-adapter-contract.md`, last lines); reality: API registry entry + `package.json` dependency + admin form + docs table + CI job.

### Inferences
- Checklist for a first-party in-repo adapter: (1) new package in `sethucms-adapters/packages/<db>`; (2) conformance live test + env var; (3) CI job in `/home/kasinadhsarma/sethucms/.github/workflows/databases.yml`; (4) dependency + registry entry in `apps/api`; (5) `ADAPTER_FORMS` entry in the admin app; (6) docs table in D/18 and README; (7) optional: migration support and `declareCollections`/`files` flags.
- Third-party without forking: gRPC process (any language, strongest isolation; credentials travel over TLS to that process; JSON-over-gRPC adds latency and the "numbers as doubles" caveat) or embed `createGateway({adapters})` in their own entrypoint. A package-plugin loader for stock `main.ts` does not exist; adding one (env var listing npm packages) would be a small gateway change but also needs an admin-form description mechanism.

### Gaps
- No documented way for a gRPC adapter to ship its own admin form (the form list is compiled into the admin app).
- TLS with a custom CA for gRPC is stated as "not tested" in D/23.

## 5. What stops gateway state from using PostgreSQL for workspaces, and how big is the change?

### Takeaway
Gateway state (not content) can live in a data folder (JSON file store), Firestore, or PostgreSQL (`SETHUCMS_STATE_URL`). Per-person workspaces are refused with PostgreSQL because the Postgres store has fixed, un-namespaced table names, a single-row state (`id = 1`), one shared audit table and global NOTIFY channels, while workspaces rely on a per-workspace namespace (Firestore collection prefix or a data subfolder). A fix is a medium-sized, well-contained change (namespace/schema per workspace), roughly one store module family (~900 lines of existing code touched), plus tests.

### Cited Findings
- The refusal: `if (db) throw new Error('SETHUCMS_WORKSPACES=open is not available with PostgreSQL shared state. Use Firestore or a data folder.')` — `/home/kasinadhsarma/sethucms/apps/api/src/boot/workspaces.ts` (42-46). Documented in `/home/kasinadhsarma/sethucms-docs/docs/30-workspaces.md` (25). No stated rationale in either file (rationale below is inferred from code).
- How workspaces are isolated today: each workspace is a full `createGateway` built per id with its own config: Firestore prefix `<prefix>_<id>` or `dataDir/workspaces/<id>`; `sqliteDir` unset, `allowPrivateNetworks: false`, no OIDC/GitHub — `/home/kasinadhsarma/sethucms/apps/api/src/boot/workspaces.ts` (79-129); `Workspaces` class keeps up to 8 gateways open, LRU-closed, ids HMAC-signed — `/home/kasinadhsarma/sethucms/apps/api/src/tenancy.ts`; doc statement "There is no shared table to forget a filter on" — `/home/kasinadhsarma/sethucms-docs/docs/30-workspaces.md` ("How it stays isolated").
- The per-workspace config is `{...rest}` of the main config, so `stateUrl` would be inherited by every workspace — `/home/kasinadhsarma/sethucms/apps/api/src/boot/workspaces.ts` (84-109), `/home/kasinadhsarma/sethucms/apps/api/src/gateway.ts` (143-144 opens `SharedDb` from `config.stateUrl`).
- Postgres store design: fixed tables `sethucms_state` (single row, `CHECK (id = 1)`, JSON `data`, `version`), `sethucms_audit` (one table, `chain` column per gateway process), `sethucms_idempotency`, `sethucms_outbox`, `sethucms_deliveries`; fixed NOTIFY channels `sethucms_state`, `sethucms_events`, `sethucms_outbox`; advisory lock key 727001; no prefix or schema option in `SharedDbOptions {url, instanceId, poolSize}` — `/home/kasinadhsarma/sethucms/apps/api/src/store/postgres.ts` (1-112, 225-260), `/home/kasinadhsarma/sethucms/apps/api/src/store/postgres-shared.ts`, `/home/kasinadhsarma/sethucms/apps/api/src/changes/postgres.ts`. Two workspaces on one DB would therefore read/write the same `sethucms_state` row and receive each other's NOTIFYs and audit rows (inference from the fixed names).
- By contrast Firestore store takes a `prefix` (validated `/^[A-Za-z][A-Za-z0-9_-]{0,40}$/`) used for all collections, which is what workspaces vary — `/home/kasinadhsarma/sethucms/apps/api/src/store/firestore-client.ts` (56-75), `/home/kasinadhsarma/sethucms/apps/api/src/gateway.ts` (193-203).
- Config forbids both backends at once: SETHUCMS_STATE_URL and SETHUCMS_FIREBASE... Firestore project set together -> error — `/home/kasinadhsarma/sethucms/apps/api/src/config.ts` (296-299).
- Other workspace-related Postgres blockers: the Postgres path passes `SharedDb` into `openWorkspaces` as `db` but each workspace gateway builds its own `SharedDb` if `stateUrl` is set (one pool + one LISTEN connection per workspace; up to 8 open) — `/home/kasinadhsarma/sethucms/apps/api/src/gateway.ts` (143-147), `/home/kasinadhsarma/sethucms/apps/api/src/boot/workspaces.ts` (open limit 2-64). Firestore case shares one client via a Proxy so closing a workspace does not terminate it (66-78); no equivalent exists for `SharedDb`.
- Gateway state is a single JSON document in the Postgres store, mirrored by `StateStore` interface (`/home/kasinadhsarma/sethucms/apps/api/src/store/state.ts`), with other backends in `store/firestore-state.ts`, file store in `state.ts`; there is no MySQL/MongoDB/SQLite state store.
- Tests that cover workspaces use data folder/Firestore fakes only: `/home/kasinadhsarma/sethucms/apps/api/tests/workspaces.test.ts`; Postgres state live tests: `/home/kasinadhsarma/sethucms/apps/api/tests/shared-state.live.test.ts`, `postgres.live.test.ts`, `worker.live.test.ts`, `schedule-shared.live.test.ts`.

### Inferences
- Change needed: add a namespace to `SharedDb`/`PostgresStateStore`/`PostgresAuditSink`/idempotency/`PostgresChangeStore`: either (a) one Postgres schema per workspace (`SET search_path`, `CREATE SCHEMA IF NOT EXISTS ws_<id>`, schema-qualified NOTIFY channel names) or (b) a `workspace` column/key in every table and in channel names plus a table-prefix option. Share a single pool across workspaces (like the Firestore proxy), and add isolation tests analogous to the Firestore ones.
- Size estimate (author's): ~3-5 files changed in `apps/api/src/store` and `changes/` (existing ≈ 900 lines), one-line change in `boot/workspaces.ts` to pass a namespace and remove the refusal, new live test, doc update. Medium effort; main risk is cross-tenant leakage via missed table/channel names and per-workspace pool/LISTEN connection count (hence the shared-pool requirement). Option (a) keeps the repo's "no shared table to forget a filter on" principle.
- Distinct from content connections: none of this affects whether a customer's content DB is PostgreSQL; a Postgres content connection works in a workspace today (Postgres adapter is registered in `builtInAdapters`).
